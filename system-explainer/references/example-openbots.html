How OpenBots works

A Bot is a run in a queue.

A message becomes a row in Postgres, a job in Redis, and a loop around a model. This page follows one through the system, figure by figure.

    The whole system

    One server process (API, WebSocket gateway, workers and a scheduler), two stores, and one sandboxed computer per owner. Everything a user sees arrives as an event on a single Redis channel. Pick a request below and watch where it goes.

      A run is a loop

      Definition 2.1A run is one job on the runs queue. It is a single streamText call that can take up to 40 steps. Each step may ask for tools; each tool result is fed back as input to the next step. The run ends when the model answers without asking for anything.

      Around that loop, OpenBots adds three things. Gating: every tool goes through gated(), which applies the Bot's policy and can park the run until someone approves. Steering: messages that arrive mid run are not queued as a new run; prepareStep drains them into the transcript before the next step. Checkpoints: the run's state is saved after steps and tool calls, so if a worker dies another one takes over (at most twice).

        What Postgres keeps, what Redis carries

        A simple rule: if losing it would lose a conversation, it lives in Postgres. Redis moves work and events between processes, and can be rebuilt. Even the per Bot run lock is a Postgres advisory lock, not a Redis one.

        Postgres

        Drizzle over postgres.js. Row level security by workspace. Secrets sealed with the master key.

        Spawning a coding agent

        Definition 5.1A coding session is a vendor CLI (Claude Code, Codex or pi) running in a git worktree inside the owner's computer, driven by OpenBots and watched by a Bot run that waits for it.

        The Bot does not write code itself. It calls the coder tool, which creates a session and parks the run. A separate coders worker starts the CLI over the computer agent's /coder socket, records every event, and turns the CLI's permission prompts into ordinary approvals. When the CLI finishes, the waiting run resumes with the commits, a diff and an optional pull request.

        Shared loginsThe owner signs in to each vendor once. That login, stored in coder_accounts, powers coding sessions and also chat models: a Bot can answer with your Claude or Codex subscription because subscriptionModel streams through the same computer while tools still run on the server.

        Commit identityCommits are authored as Bot name (OpenBots) with the owner as co-author, unless the owner chooses to commit as themselves.
        Two runs cooperate: the Bot run and the coder session.

          Phones, the relay, and coming back

          A self hosted server usually has no public address. So the server dials out to openbots-relay and holds a host link, but only while some device is paired. The phone connects to the same relay, and the relay pipes bytes between them. Inside that pipe is a Noise IK tunnel carrying ordinary HTTP and WebSocket traffic, encrypted end to end. The relay sees ciphertext.

          Pushes take the same road. The push worker listens on openbots:events, encrypts a payload with the device's push key, and sends it up the host link. The relay forwards it to APNs, and the phone's notification extension decrypts it.

          The relay itself runs as several Fly Machines. A Redis registry records which Machine owns each host; a Machine that gets a phone for a host it does not own answers with fly-replay.

          When the app returns to the foreground

          1. Going to the background closes the socket. Encrypted pushes cover the gap.
          2. On return, try direct URLs first, with a 2.5 s timeout.
          3. Fall back to the relay tunnel.
          4. Resubscribe to chats, then GET /resync?since=seq to fetch what was missed.
          5. Drop duplicate deltas by number. Retry with backoff from 500 ms to 30 s; stale handshakes are ignored.
          7

          System design, as deployed

          The default install is one Compose stack. The server never touches the Docker socket directly: docker-guard filters every call, and computers sit on their own network behind an iptables firewall. The relay is the only shared piece, and it never holds keys.

          Five imagesserver, computer, sandbox-firewall, relay and standalone. On Fly, the openbots app runs standalone: server, Postgres, Redis and the computer in one container under s6, with a /data volume and a /readyz check. The server can also be split by OPENBOTS_ROLE into api and worker processes that share the same Postgres and Redis.
